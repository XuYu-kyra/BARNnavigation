## 2. Persistent fault characterisation

### 2.1 为什么做 persistent fault

老师提出了 duration 的质疑：如果 masking 的现实解释是 dirt / mud / foreign object blocking LiDAR，那么为什么 20 秒后 fault 自动消失？

因此将 fault duration 分成两个层级：

| Study | Fault duration | 研究目的 |
|---|---:|---|
| Study A: transient campaign | 20s, active 15-35s | performance degradation and propagation characterisation |
| Study B: persistent pilot | active from start time until end | recovery stress condition / recoverability |

这避免推翻已有 formal campaign，同时补上对 persistent fault 的解释。

### 2.2 参数设置

| Parameter | Value | Justification |
|---|---:|---|
| Persistent fault start | 15s | 与 formal campaign fault onset 一致，避免污染 Nav2 初始化。 |
| Persistent duration | until success / timeout | 用于测试 fault 不自行消失时系统是否仍可导航。 |
| Initial worlds | W8 masking, W240 dropout | 分别代表两个 fault branch 的已知 representative cases。 |
| Timeout | 300s | 与 formal campaign 保持一致。 |

### 2.3 结果摘要

W8 persistent masking：

- 6 pairs completed。
- mean paired slowdown: `+3.942s`
- 95% CI half-width: `1.622s`
- 说明 persistent masking 在 W8 中没有制造不可恢复 failure，而是表现为 mild slowdown。

W240 persistent dropout：

- 后续通过 campaign runner 补齐 6 pairs。
- 观察到 fault-only 和 recovery-filter 条件均可运行。
- 没有稳定证明 dropout recovery filter 带来 performance benefit。

其他 persistent masking screening：

| Condition | Worlds | Result |
|---|---|---|
| 90 degree persistent masking | W86, W250, W76, W239 | 多数成功，W173 startup/launch invalid excluded |
| 180 degree persistent masking | W239, W250, W76, W86 | 全部成功 |

记录到的代表性结果：

| World | Fault | Width | Outcome |
|---:|---|---:|---|
| W86 | persistent masking | 90 deg | success, `101.7940s` |
| W250 | persistent masking | 90 deg | success, `142.1431s` |
| W239 | persistent masking | 90 deg | success, `114.1489s` |
| W239 | persistent masking | 180 deg | success, `119.1217s` |
| W250 | persistent masking | 180 deg | success, `137.4712s` |
| W76 | persistent masking | 180 deg | success, `104.6861s` |
| W86 | persistent masking | 180 deg | success, `112.9712s` |

### 2.4 解释

Persistent fault 没有稳定产生“必须 recovery 才能成功”的场景。该结果说明：

- Nav2/BARN 在部分 worlds 中对 frontal LiDAR degradation 有较强鲁棒性。
- Persistent fault 适合作为 stress/sanity observation，而不是替代主 transient campaign。
- 后续 recovery 不应强行 claim performance improvement。

## 3. Classifier 子项目

## 3.1 Stage 0: injector semantics audit

### 目的

确认两个 LiDAR fault 在实际 ROS graph 和 LaserScan message 中如何表现，避免基于错误假设设计 classifier。

### 检查内容

- `/front/scan`
- `/front/scan_faulted`
- `/fault/scan_active`
- local/global costmap subscriptions
- QoS
- scan frequency
- injector code logic

### 关键发现

最重要发现：

```text
Dropout is not message-level dropout.
It is sector-level periodic range replacement.
```

也就是说，dropout 不是整条 LaserScan 消失，而是 front sector 在 dropout burst phase 中被替换为 `range_max`。这直接影响 classifier 设计。

两类 fault 的关系变得清楚：

```text
Masking:
frontal sector degraded continuously

Dropout:
frontal sector degraded / healthy / degraded / healthy
periodic switching
```

### `/fault/scan_active` 语义

`/fault/scan_active` 表示 fault episode window，而不是 dropout burst ON/OFF phase。

例如 dropout：

```text
/fault/scan_active = true for the whole dropout episode
but scan content alternates between degraded phase and healthy phase
```

这对后续 classifier 非常关键：

- `/fault/scan_active` 可以作为 episode trigger。
- 不能用它直接得知 fault type。
- fault type 必须从 `/front/scan_faulted` 的 scan signature 判断。

### 结果

Stage 0 没有推翻前面的实验。相反，它确认：

- fault injection 确实进入 Nav2 consumed scan path。
- local/global costmap 订阅的是 `/front/scan_faulted` 或 recovered scan path。
- 之前 formal campaign 不是白跑。

## 3.2 Stage 1: scan signature diagnostics

### 目的

验证两个 fault 在实际 scan signature 中是否可分离。

### 初始问题

第一次 Stage 1 图中，fault window shading 和 feature extraction 不匹配，导致 masking/dropout 看起来不明显。后来修正 timestamp / fault window alignment 后，signature 变清楚。

### 关键特征

使用最小 feature set：

| Feature | 含义 |
|---|---|
| frontal range_max ratio | frontal sector 中接近 range_max 的 beam 比例 |
| largest contiguous range_max span | 最大连续 degraded frontal sector 占比 |
| degraded fraction over temporal window | window 内 degraded scan 比例 |
| switching rate | degraded/healthy 状态切换频率 |
| longest degraded streak | 连续 degraded 持续时间 |
| longest healthy streak | 连续 healthy 持续时间 |

### 观察结果

Masking：

```text
frontal degradation sustained
switching rate near 0
long degraded streak
```

Dropout：

```text
degraded and healthy phases alternate
switching rate high
both degraded and healthy streaks observed
```

因此 classifier 定义为：

```text
spatial detection + temporal identification
```

## 3.3 Stage 2A: autonomous sliding-window classifier

### 设计

Stage 2A 目标是 continuous classifier：

```text
NORMAL / MASKING / DROPOUT / UNKNOWN
```

它完全依赖 scan content，不使用 `/fault/scan_active`。

### 失败原因

Stage 2A 没有通过，主要问题是 normal false alarm。

原因：

- BARN world geometry 本身可能产生大量 `range_max`。
- 前方开放区域在正常情况下也可能看起来像 high range_max。
- 单纯 scan-only sliding window 很难稳定区分 “normal open space” 和 “fault-induced range_max sector”。

结论：

```text
Stage 2A insufficient for deployment.
```

这不是项目失败，而是说明 autonomous fault-presence detection 是更难的问题，不应在本 dissertation 中扩张。

## 3.4 Stage 2B: conditional episode-level fault-type classifier

### 调整后的研究问题

将 classifier 任务收缩为：

```text
Given a fault-presence trigger, identify whether the LiDAR fault episode is MASKING or DROPOUT.
```

换句话说：

- `/fault/scan_active` 提供 fault episode trigger。
- classifier 不读取 injector type。
- classifier 在 episode 内观察 `/front/scan_faulted` 2 秒。
- 输出一次 fault type 并 latch。

### 为什么这样合理

因为 recovery 真正需要的是：

```text
fault exists
→ which recovery policy should be selected?
```

而不是每一秒都完整判断 normal/fault/fault type。

### 参数选择

| Parameter | Value | Justification |
|---|---:|---|
| Observation window | 2s | dropout period = 1s, duty = 0.5，因此 2s 可覆盖两个 dropout cycles，同时 latency 可接受。 |
| Dropout min switching rate | 0.75/s | dropout 应表现出 degraded/healthy switching。 |
| Masking max switching rate | 0.55/s | masking 应持续 degraded，切换频率低。 |
| Masking min degraded fraction | 0.55 | 超过半数 window 呈现 sustained degradation 才判断 masking。 |
| Dropout min degraded fraction | 0.15 | dropout 只在部分 phase degraded，因此阈值低于 masking。 |
| UNKNOWN branch | enabled | weak/conflicting evidence 时拒绝选择 fault-specific recovery，避免 wrong policy。 |

### Development validation

Development episodes：

- 6 episodes
- masking 3/3 correct
- dropout 3/3 correct
- wrong type = 0
- UNKNOWN = 0

### Held-out validation

Held-out worlds：W173, W274

| World | Ground truth | Predicted | Latency | Degraded fraction | Switching rate | Result |
|---:|---|---|---:|---:|---:|---|
| W173 | DROPOUT | DROPOUT | 2.0s | 0.5125 | 2.025/s | correct |
| W173 | MASKING | MASKING | 2.0s | 1.0000 | 0.000/s | correct |
| W274 | DROPOUT | DROPOUT | 2.0s | 0.5000 | 2.025/s | correct |
| W274 | MASKING | MASKING | 2.0s | 1.0000 | 0.000/s | correct |

Summary：

- episode count = 4
- correct = 4
- wrong type = 0
- UNKNOWN = 0
- mean identification latency = 2.0s

### Stage 2B conclusion

```text
The conditional episode-level classifier was implemented and validated for the two studied LiDAR fault types.
```

但不能写成：

```text
universal autonomous LiDAR fault diagnosis
```

## 4. Recovery prototype work

## 4.1 Recovery Policy 0: velocity scaling

### 设计

最早的 recovery 是简单降低速度：

```text
fault active
→ scale linear/angular cmd_vel
```

### 问题

老师和实验都显示该策略太弱：

- 如果 LiDAR front sector 看不见，单纯减速不会恢复新信息。
- persistent fault 下，等待或变慢不会修复 sensor observation。
- 不适合作为 main recovery contribution。

### 结论

保留为 negative pilot：

```text
command-level slowdown is insufficient as a fault-aware recovery strategy.
```

## 4.2 Masking Recovery v1: cmd_vel-level reorientation

### 设计

```text
masking detected / progress stalled
→ override cmd_vel
→ rotate robot 60 degrees
→ settle
→ release Nav2
```

参数：

| Parameter | Value | Justification |
|---|---:|---|
| rotation angle | 60 deg | 改变 front blind sector 观察方向，但不完全破坏原导航朝向。 |
| angular speed | 0.45 rad/s | 保守转向速度，避免过激运动。 |
| settle duration | 1s | 给 scan/costmap 更新时间。 |
| stall window | 5s | 避免正常微调时误触发。 |
| stall distance | 0.05m or 0.15m depending on test | 5 秒几乎无位移才认为 progress stall。 |

### 结果

Recovery action 本身执行成功，但 Nav2 task-level 状态没有被重新协调。典型日志：

```text
Masking reorientation recovery started
rotation complete
recovery complete
Failed to make progress
Goal failed
```

W8 和 W240 均出现 repeated `Failed to make progress` / `Goal failed`。

### 结论

```text
Low-level cmd_vel intervention is insufficient because it does not coordinate with Nav2 action/costmap/task state.
```

## 4.3 Masking Recovery v2: Nav2 action-level M2 supervisor

### 设计

将 masking recovery 改为 Nav2 action-level：

```text
fault/progress trigger
→ cancel current NavigateToPose
→ clear local costmap
→ Spin 60 degrees
→ settle
→ resend NavigateToPose goal
```

### 结果

Forced M2 能执行并完成：

| World | Condition | Outcome |
|---:|---|---|
| W8 | forced M2 | success, about `107.6900s` |
| W240 | forced M2 | success, about `114.9567s` |

Progress-gated M2：

- W8 success, about `87.1614s`。
- W240 success, about `91.6376s`。
- 多数情况下并未真正需要 active M2，因为 progress 没有达到 stall trigger。

### 结论

M2 supervisor 证明了 task-level recovery architecture 可执行，但没有证明 performance benefit。

## 4.4 Dropout Recovery: temporal perception gating

### 设计理由

Dropout 不是持续遮挡，而是 intermittent corrupted scan burst。因此不应简单 stop/wait，而应过滤不可信 burst。

设计：

```text
/front/scan_faulted
→ dropout_scan_recovery_filter
→ /front/scan_recovered
→ Nav2
```

当 fault episode active 且 frontal sector range_max ratio 超过阈值：

```text
replace affected frontal beams with NaN
```

这样做的含义：

- 不把 dropout burst 当成可靠 free-space evidence。
- healthy phase 保持 pass-through。

参数：

| Parameter | Value | Justification |
|---|---:|---|
| range_max ratio threshold | 0.55 | 超过半数 frontal beams 接近 range_max，认为该 scan phase 不可信。 |
| near range_max fraction | 0.98 | 允许数值误差，把接近 range_max 的 beams 归为 dropout evidence。 |
| output topic | `/front/scan_recovered` | Nav2 可订阅 recovered scan path。 |

### Bug fix

初始实现未正确把 `inf` beams 计入 corrupted/near-range-max，导致 filter 没有正确 active。修正后可观察到：

```text
Dropout recovery filter active: rejecting frontal dropout bursts
```

### W8 smoke result

W8 dropout filter smoke：

- filter active observed。
- navigation success: `90.9340s`
- metric: `0.1250`

### 3-pair pilot result

W240 fault-only vs dropout filter pilot：

| Condition | Result summary |
|---|---|
| W240 dropout fault-only | success 3/3, mean slowdown about `+2.96s` |
| W240 dropout + filter | success 3/3, mean slowdown about `+5.11s` |

W8 filter pilot：

- only 2 complete pairs usable。
- observed paired differences about `+19.36s` and `+12.13s`。
- third baseline hard timeout, therefore incomplete/unusable for formal conclusion。

### Conclusion

```text
Dropout filter is functionally implemented and can be activated, but it does not demonstrate performance improvement.
```

## 5. Closed-loop classifier-to-policy integration

## 5.1 Why this was needed

Before this step, components were tested separately:

```text
fault injector ✓
Stage 2B classifier ✓
masking recovery prototype ✓
dropout filter prototype ✓
automatic selector/routing ✗
```

The missing question was:

```text
Can the system automatically identify the injected fault type and route to the corresponding recovery policy without using injector mode as an oracle?
```

## 5.2 Implemented architecture

```text
/front/scan
→ fault injector
→ /front/scan_faulted
→ dropout recovery filter, default pass-through
→ /front/scan_recovered
→ Nav2
```

Parallel supervisory path:

```text
/fault/scan_active
→ observe /front/scan_faulted for 2s
→ Stage 2B classifier
→ MASKING / DROPOUT / UNKNOWN
→ selector publishes:
   /recovery/dropout_filter_enable
   /recovery/masking_monitor_enable
```

### Important design rules

- Selector does not read `scan_fault_mode`.
- Injected fault type is only ground truth for post-run evaluation.
- UNKNOWN disables fault-specific recovery.
- Dropout filter remains in path but pass-through by default.
- Masking supervisor remains disabled until selector outputs MASKING.

## 5.3 Initial closed-loop failure

First closed-loop attempt did not pass.

Symptoms:

- Nodes launched correctly。
- fault episode detected。
- W8 masking/dropout returned `UNKNOWN`。
- W240 runs did not consistently produce `fault_type_estimated` before finishing。

Cause:

The selector initially used only baseline-delta evidence:

```text
degraded = fault_window_signature - pre_fault_baseline
```

But in some BARN geometry, pre-fault baseline already had high `range_max_ratio`:

```text
baseline_range_max_ratio=1.000
baseline_span_ratio=1.000
```

Therefore the delta was zero even during fault, causing:

```text
predicted_type=UNKNOWN
```

## 5.4 Adjustment

The classifier was adjusted for closed-loop mode:

```text
Because /fault/scan_active already indicates a fault episode,
the classifier should identify fault type using absolute fault-window scan signature,
not only baseline increase.
```

This is not a new fault campaign; it is an integration robustness fix. It preserves Stage 2B principle:

```text
fault presence trigger + scan-based fault type identification
```

## 6. Parameter justification summary

| Parameter | Value | Used in | Justification |
|---|---:|---|---|
| Formal fault start | 15s | main campaign / formal sanity check | Allows Nav2 and costmaps to initialize before fault. Represents fault occurring during active navigation. |
| Smoke fault start | 5s | closed-loop integration smoke | Forces early fault episode so classifier and selector can be observed. Not used for performance comparison. |
| Fault duration | 20s | transient campaigns and smoke | Long enough to cover multiple planner/controller cycles and two dropout cycles, short enough to avoid turning every run into timeout. |
| Persistent fault | until run end | persistent pilot | Tests recoverability when fault does not self-clear. |
| Sector center | 0 deg | all scan faults | Directly affects frontal navigation sector. |
| Sector width | 90 deg | main LiDAR fault tests | Strong frontal degradation without becoming full 360 degree sensor loss. |
| Dropout period | 1.0s | dropout fault | Creates clear temporal switching signature. |
| Dropout duty cycle | 0.5 | dropout fault | Equal bad/healthy phases make intermittent pattern identifiable. |
| Stage 2B observation window | 2s | classifier / closed-loop | Captures approximately two dropout cycles while keeping response latency low. |
| Dropout filter threshold | 0.55 | recovery filter | If more than half of frontal beams are near range_max, scan phase is treated as unreliable. |
| Near range_max fraction | 0.98 | filter and feature extraction | Handles numeric tolerance around range_max. |
| M2 rotation angle | 60 deg | masking recovery | Changes observation direction without fully reversing task orientation. |
| Stall window | 5s | masking recovery trigger | Avoids triggering recovery during normal small controller adjustments. |
| Stall distance | 0.05m | masking M2 progress trigger | 5 seconds with almost no displacement indicates genuine progress stall. |
| Benchmark timeout | 300s | formal comparison | Consistent with main BARN campaign. |
| Outer process timeout | 420-720s | smoke/debug runs | Allows benchmark timeout plus ROS/Gazebo cleanup buffer. |

|---|---|---|---|---|

## 8. Final evidence hierarchy

### Strong evidence

- Formal two-fault campaign completed and analysed.
- Stage 2B classifier correctly identifies masking/dropout on development and held-out episodes.
- W8 closed-loop smoke validates both classifier-to-policy branches.

### Moderate evidence

- Dropout filter and masking M2 recovery components are executable and can be activated.
- Persistent and early-onset fault runs show system behaviour under stronger stress.

### Negative or limited evidence

- Recovery strategies did not demonstrate reliable performance improvement.
- Correct classifier output and policy routing do not guarantee task success.
- W240 start=5 masking collision shows recovery remains incomplete.

```text
A lightweight conditional fault-type classifier was implemented for the two studied LiDAR fault models. Given a fault-presence episode trigger, the classifier uses a two-second window of the navigation-consumed LiDAR stream to distinguish sustained frontal masking from intermittent dropout. A W8 closed-loop smoke test then demonstrated automatic classifier-to-policy routing for both fault branches. However, recovery effectiveness was not established: although the corresponding recovery components could be activated, task-level outcomes remained world- and timing-dependent. These results support the supervisory integration concept while identifying recovery policy design as future work.
```
